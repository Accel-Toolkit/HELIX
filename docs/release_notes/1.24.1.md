# HELIX 1.24.1 — BLAS on one thread in every run, whichever thread runs it

Released 2026-11-10.  With threadpoolctl 3.7 or 3.8, a run in a thread
other than the first run's could keep BLAS on all its threads while
recording one.  Every run now holds BLAS on one thread in its own thread,
and the results file records 1 only when it does.  Results do not change.

## Fixed

* **BLAS stays on one thread in every run, whichever thread runs it.**
  threadpoolctl 3.7 and later limit MKL, and OpenBLAS built on OpenMP, in
  the calling thread only; 3.8 also lets one thread at a time set an
  OpenBLAS pool the whole process shares (OpenBLAS built with pthreads or
  Windows threads, as in numpy's and scipy's pip wheels for Linux and
  Windows): the first thread that sets it, while that thread lives; the
  others are ignored.  HELIX limited BLAS once, from the first of
  overlapping runs, and never let go of such a pool.  So with 3.8, once
  the thread of a first run lived on (a server or script thread), a run in
  another thread kept BLAS on all its threads and still recorded
  `threads_blas = 1`; with MKL or OpenBLAS on OpenMP (threadpoolctl 3.7 and
  later), a run overlapping another in a second thread was not limited at
  all, and the first run's thread could stay on one BLAS thread after both
  ended.  GUI runs were not affected: the GUI starts BLAS on one thread.
  Each run now limits BLAS as its own thread sees it: a library limited per
  thread in each run's thread, until that run ends; a pool the process
  shares by the first of overlapping runs, until the last of them ends,
  taking the pool for each change and letting go of it at once.  The first
  time a library is held, its count read from a second thread before and
  after tells which kind it is.  `threads_blas` is 1 only when every BLAS
  library threadpoolctl sees at the run's start reads one thread in the
  run's thread once limited; it is absent otherwise, also when threadpoolctl sees no
  BLAS library (Apple's Accelerate), where it used to say 1.  Results do not
  change: an envelope run and a 10,000-particle run on the first 400
  elements of a 2907-element linac give identical arrays with BLAS at 1 and
  at 14 threads, and that linac and a LEBT plus RFQ give results identical
  to 1.24.0's.  Runs that missed the limit were slower.  With threadpoolctl
  3.6 or older, runs limit BLAS as before.
