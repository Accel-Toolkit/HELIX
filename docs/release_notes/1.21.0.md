# HELIX 1.21.0 — ring mode

Released 2026-10-28.  Ring mode for synchrotrons: tracking turn after turn at
fixed energy or through a ramp, with space charge and H- injection through a
stripping foil.

## Ring mode (new, opt-in)

A linac session never sees ring mode: ring mode changes no linac result, and
a linac project is saved exactly as before (the changes outside ring mode,
listed below, can change results).  numba (the `[ring]` extra) compiles ring
mode's kernels; without it they run as plain Python, far more slowly.

* **Switching it on.**  Simulate → Ring Mode adds the Ring tab.  A lattice
  whose horizontal bends add up to 360° and whose survey closes (or a deck
  that declares `;@LG ring`) gets a note offering it.
* **Optics.**  Tunes with their integer part, chromaticities, momentum
  compaction, slip factor and transition gamma, the periodic Twiss functions
  and dispersion; with the RF on, the 6-D closed orbit, the synchrotron tune
  and the RF bucket.  Two element models: Cartesian bend multipoles, as
  MAD-X decks define them, or exact elements with the bend multipoles in the
  curved frame; exact, full or linear pole faces.
* **The beam.**  A ring run starts from the Beam tab's beam, as a linac run
  does: one distribution, one number of particles, one set of Twiss
  functions.  Ring & Optics → Use the matched beam in the Beam tab gives the
  Beam tab the beam matched to the ring at the start of the run (the Twiss
  functions x, y and, with the RF on, z, the dispersion and the closed
  orbit, from the optics of the run's first turn, a ramp's included), and
  a run that starts with a beam gives that beam's BMAG.  The command line
  runs a project's beam (a bare lattice file: a Gaussian matched to the
  ring).  A MAD-X or MAD8 deck whose `BEAM` gives the energy sets the ring's
  energy; a deck that states none (TraceWin, elegant, a MAD-X `BEAM` with
  only the particle) runs at the Beam tab's, and a deck of normalized
  strengths keeps them there.
* **Runs.**  A bunch turn after turn at fixed energy or through a ramp, on
  every CPU core (the same bits for any number of threads) or on an NVIDIA
  GPU through numba's CUDA compiler in double precision (not yet run on a
  GPU: see below); apertures and the
  particles lost where and when; snapshots; NAFF tunes and tune footprints;
  checkpoints from which a run continues bit for bit; results in HDF5.
* **The ramp.**  Energy programs (flat, a resonant cycle, a table), RF
  voltage and phase programs, transition crossed with its phase jump,
  paraphasing; the magnets follow the reference momentum; a preview of the
  reference particle alone through the ramp.
* **Space charge.**  The 2.5-D model — the transverse field of the beam's
  distribution on a grid (or of a frozen Gaussian) times the line density —
  in an open, round, rectangular or elliptic pipe, with the longitudinal kick
  of the line density's slope.  By default the line density's bins follow
  the bunch's length (16 bins per rms of its core) and the line density is
  smoothed over a width chosen from the number of particles (a kernel-density
  bandwidth): the noise of few particles heats the beam far less (through
  transition, 5000 particles now grow as 20 000 do); a run notes when the
  bins and the smoothing do not resolve the bunch.
* **Injection.**  An H⁻ beam (the Beam tab's, a particle file or a
  Gaussian) stripped in a foil — scattering by Highland's formula at the
  total thickness each particle has crossed, energy loss, stripping — with
  chopping, and bump and painting magnets driven by waveforms; the foil's
  hits and deposited energy, and the ledger of every particle injected,
  circulating, lost or wasted.
* **Where.**  The GUI's Ring tab (Ring & Optics, Programs, Space charge,
  Injection, Run, with a live strip of the survival and emittances while a
  run goes); the Results tab, where a ring run is shown turn by turn in the
  existing tiles (Run shown: Linac run | Ring run) and RING RUN adds the
  ramp, the bunch in eV·s, the losses, the tune diagram, phase space at the
  snapshot turns, the periodic optics and the injection; ring results files
  keep the run's periodic optics table (`/optics_table`);
  `python -m linac_gen ring optics | ramp | run`; the Python API
  (`linac_gen.ring`); the AI assistant's ring tools (`ring_status`,
  `ring_optics`, `ring_programs`, `set_ring_program`, `set_ring_mode`,
  `run_ring`, and `run_in_gui` with kind `ring`).
* **Manual.**  Chapter 17 (ring mode: optics, element models, runs, the
  ramp, space charge, injection, GPU runs, a first ring run in the GUI, the
  command line, the results files) and the validation pages: analytic
  results, and comparisons with reference codes on public lattices.
* **GPU.**  Ring mode's CUDA kernels have been checked in numba's CUDA
  simulator only; they have not yet run on an NVIDIA GPU.
  `python scripts/verify_cuda_ring.py --quick` checks a GPU against the CPU.

## Changes outside ring mode

These can change existing results; each is listed with what it affects.

* **MAD-X import reads a deck the way MAD-X does** (each rule pinned to
  MAD-X 5.09): `LINE=(…)` beam lines (nesting, repetition, reversal),
  inheritance, `:=` and `elem->attr` modifications, undefined names taken
  as 0, IF/ELSE, WHILE and MACRO/EXEC as MAD-X runs them, `at :=`, `l :=`
  and `from=` positions.  Results that change: a second BEAM now merges into
  the first (it replaced it — an H⁻ beam became a proton and every gradient
  flipped); bends with TILT = π/2 are vertical and TILT = π bends the other
  way; `HARMON` sets the RF frequency (a HARMON-only cavity had frequency 0,
  or 352.21 MHz in multiparticle runs) and overrides FREQ; a bend's K0 and
  K2 are kept for ring mode (linac tracking ignores them and says so); a
  sequence inside a sequence is named as such in the warning.  Kickers:
  HKICKER and VKICKER read KICK, or HKICK/VKICK when KICK is zero, plus
  CHKICK/CVKICK; KICKER and TKICKER both planes; TILT rolls the kick —
  decks whose kickers set HKICK=/VKICK= (as MAD-X's SAVE writes them) now
  kick.
* **MAD8 and elegant import:** MAD8 bends follow the same tilt rule; MAD8
  and elegant keep a bend's K2 (for ring mode) and say so.
* **RF gap:** a gap with a voltage but no positive frequency raises an
  error naming it (it divided by zero).
* **MAD-X import, FINTX:** a negative FINTX (MAD-X's default is −1) now
  means the same as FINT, as in MAD-X.  It was taken as an exit-face fringe
  integral of −1: R43 −2.0e-4 instead of MAD-X's +4.0e-4 for a 0.1 rad bend
  with HGAP 0.02 and FINT 0.5.  Decks without FINTX, or with FINTX ≥ 0, are
  unchanged.
* **MAD-X import, skew components:** a quadrupole's K1S and a sextupole's
  K2S turn the magnet as MAD-X does: √(k1² + k1s²) at TILT − atan2(k1s, k1)/2,
  and the same with /3 for a sextupole.  They were dropped without a word.  A
  bend's K1S and K2S are reported as not modelled (MAD-X's TWISS leaves them
  out too).
* **MAD-X thin bends:** a MULTIPOLE with a dipole component (KNL[0] or
  KSL[0]) or an ANGLE is now reported on import.  MAD-X bends the reference
  orbit there; HELIX imports the dipole part as a kick about a straight
  reference, so a lattice converted to thin elements imports without its
  bends.  The export warns the other way (a Multipole's knl[0]/ksl[0] is a
  thin bend in MAD-X), and so does an exit edge with a negative fringe
  integral, which MAD-X reads as FINT.
* **TraceWin decks:** `;@LG` lines read several key=value pairs, as the
  manual describes; a value runs to the next key= (`note=booster ring study`
  stays one value, as in 1.20), and a key on its own before the pairs is a
  flag.  Save Lattice writes the deck's `;@LG` lines back (they were dropped,
  so a saved ring deck lost its `;@LG ring`).
* **Import metadata:** the MAD-X, MAD8, elegant and Bmad/SciBmad/PALS imports
  return `metadata["reference_declared"]`, saying whether the deck itself
  gives the beam energy.
* **Foil element:** Highland's width with the logarithm of x z²/(X₀β²), as
  Lynch and Dahl and the Particle Data Group give it (it was x/X₀ alone):
  θ₀ is 2.3 % larger for 800 MeV protons through 600 µg/cm² of carbon, and
  20 % larger for the 24 MeV protons of the reliability demo's foil (the
  ratio depends on the energy and the thickness).  Runs through foils change
  accordingly.
* **Foil materials:** titanium and dry air at 1 atm (PDG 2024 values), for
  extraction windows and lumped in-air flight paths.
* **Edge:** the fringe term tan(ψ)/ρ acts at zero pole-face angle too (a
  sector bend with a fringe gap); every face with an angle, and every square
  face without a gap, gives the same bits as before.
* **Quadrupole:** the g3–g6 multipole kicks take the sign of the charge (H⁻
  beams got them with the wrong sign); protons, deuterons and alphas are
  unchanged.
* **MAD-X export:** each bend face keeps its own fringe term (a split
  magnet's inner faces no longer get one).
* **SET_SYNC_PHASE:** the phase offset is solved on the circle; near ±180°
  the iteration could stop at a wrong phase without a warning.
* **Results tab:** the Σ matrix along s — the 21 independent terms of the
  recorded beam matrix in a non-modal window.  The KPI strip shows "—" for a
  value the run shown does not have (an envelope run shown after a
  multiparticle run used to keep the multiparticle run's transmission and
  loss).
* **Packaging:** wheels carry the licence texts of the code ported into ring
  mode (`THIRD_PARTY_NOTICES.md`, `licenses/`).
* **Windows one-click setup:** `setup.bat` takes the newest Python that torch
  publishes wheels for (3.13, 3.12, 3.11, then 3.10) before the newest one
  installed, which can be too new for torch; an install that fails says so.
